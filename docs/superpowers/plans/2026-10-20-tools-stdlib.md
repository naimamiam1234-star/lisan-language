# خطة المكتبة القياسية والحزم والمحرر لـ 1.0

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** مكتبة قياسية أصلية قابلة للتحقق وحزم مقفلة وخدمة محرر تشترك في واجهة اللغة.

**Architecture:** سجل builtin واحد وواجهات قيم مُدارة، وحل حزم صريح قبل البناء، وتحليل ساكن مشترك للـ CLI وLSP.

**Tech Stack:** Rust، runtime أصلي، TOML/SemVer، Git، JSON-RPC/LSP وVS Code.

**Spec:** `docs/LANGUAGE-1.0-SCOPE.md` و`docs/superpowers/specs/2026-10-20-native-hardware-web-design.md`.

## Global Constraints

- لا مفسّر في اختبارات المكتبة الأصلية، ولا parser أو checker موازٍ خاص بالمحرر.
- نتائج I/O قابلة للمعالجة، وملكية القيم تابعة للعقد المشترك.
- لا جلب شبكة أو تشغيل حزم أثناء فتح المحرر أو التجميع المعتاد.

## Review Focus

- اختلاف native/legacy: المرحلة 1 تجرد التواقيع وتختبر التنفيذ الأصلي.
- فشل I/O تحت root: المرحلة 2 تحقن الفشل بدل الاعتماد على chmod.
- اعتماد متغير أو cache تالف: المرحلة 3 تثبت المراجعة وبصمة الشجرة وتفشل offline بوضوح.
- emoji قبل معرف عربي: المرحلة 4 تختبر التحويل من byte Span إلى UTF-16.
- تشخيص قديم بعد تعديل أحدث: المرحلة 4 تمنع نشر نتيجة لإصدار مستند منتهي.

الحالة: خطة تنفيذ مقترحة، 2026-10-20؛ لا تعني أن الواجهات أدناه موجودة. تنفذ كل مرحلة كتغيير مستقل قابل للمراجعة.

المرجع الملزم للنطاق: [LANGUAGE-1.0-SCOPE.md](../../LANGUAGE-1.0-SCOPE.md). الاعتماد المشترك: [خطة نواة المترجم](2026-10-20-compiler-core.md)، خصوصًا `SourceMap` و`Span` و`Diagnostic` والشجرة ذات المواقع وchecker وtyped IR وإدارة ذاكرة القيم. لا تُنشأ نسخة ثانية من parser أو نظام أنواع خاص بالمكتبة أو LSP. العتاد وDOM والشبكات خارج هذه الخطة؛ لا يُستعمل المفسّر لإكمال اختبار قبول أصلي.

## 1. سجل API للمكتبة ومجموعة القبول

**الملفات المقترحة:** `src/stdlib/mod.rs`، `src/stdlib/registry.rs`، `docs/STDLIB-1.0.md`، `tests/stdlib_registry.rs`، `tests/stdlib_native.rs`؛ تعديل checker والتوليد عند نقاط تسجيل الدوال فقط.

- [ ] جرد كل builtin في `src/runtime.rs` و`src/native.rs` ومقارنته بـ `docs/SYNTAX.md`؛ إصدار جدول «مفسّر/أصلي/غير منفذ» لكل توقيع، دون نقل ادعاءات المفسّر إلى الأصلية.
- [ ] تعريف `BuiltinId` ثابت داخليًا و`BuiltinSpec { id, name, signature, capability, failure }`. تستعمل `signature` أنواع الخطة المشتركة؛ `Capability` يميز `Core` و`HostFiles`؛ `Failure` يميز `Infallible` و`Recoverable` و`Trap`. لا يحمل السجل مؤشرات لمفسّر أو شيفرة LLVM نصية.
- [ ] ربط الأسماء بالتواقيع في checker من السجل، وتوليد الاستدعاء حسب `BuiltinId`. تكون محولات المفسّر منفصلة؛ رفض capability غير المتاح تشخيص قبل التوليد. لا يُعلن API حتى تتوفر شيفرته الأصلية.
- [ ] تثبيت API 1.0 في جدول موحد: الاسم، المعاملات والنتيجة، النسخ/الاقتراض، الأثر الجانبي، الأخطاء، الوحدة والأهداف. تضم المجموعة الطباعة والتحويلات والرياضيات والنصوص والمجموعات والمدى والتحققات والملفات حسب عقد النطاق.
- [ ] اختبار تطابق السجل/الوثيقة، تكرار الأسماء، عدد الوسائط والأنواع ورفض البيئة غير الملائمة. لكل builtin حالة نجاح وحدود/فشل عند انطباقها، تبني وتشغّل ملف آلة. اختبارات السجل وحدها لا تغطي التنفيذ.

**بوابة:** لا تأشير لاكتمال stdlib قبل اكتمال أنواع النصوص والمجموعات وملكيتها في خطة النواة؛ يمكن إنجاز APIs العددية المستقرة أولًا دون اصطناع أنواع محلية بديلة.

## 2. نتائج قابلة للمعالجة وملفات المضيف

**الملفات المقترحة:** `docs/RESULTS.md`، `src/stdlib/host_files.rs`، `runtime/host/files.c` عند الحاجة، `tests/native_results.rs`، `tests/native_files.rs`؛ تعديل الأنواع/checker/typed IR/runtime المشترك بتنسيق مع خطة النواة.

**اقتراح صريح يحتاج تثبيتًا في مواصفة اللغة قبل التنفيذ:** نوع داخلي `Result<T>` بحالتين `Ok(T)` و`Err(Error)`، و`Error { code: ErrorCode, message: Text }`. ليس نتيجة f64 ذات قيمة خاصة، ولا استثناء Rust. لا يتطلب generics عامة للمستخدم؛ ينشئ checker فقط تطبيقات الأنواع اللازمة. تُحدد صياغة عربية لبناء الحالتين وتفكيكهما في `RESULTS.md` مع قواعد grammar واختبارات قبل تعديل parser؛ لا توثق هذه الخطة كلمات جديدة كأنها مدعومة.

- [ ] تقرير تصميم قصير يثبت صياغة تفكيك exhaustive للحالتين، منع استعمال قيمة نجاح قبل التفكيك، وتمرير/إرجاع النتيجة وإدارة ملكيتها؛ لا implicit unwrap ولا تجاهل صامت لأخطاء I/O.
- [ ] إضافة tagged union إلى الأنواع والـIR والتمثيل الأصلي؛ حقل tag منفصل وpayload مطابق للهدف، وتحرير الحالة النشطة فقط. لا يُعتمد layout اللغة ABI عامًا لـ C.
- [ ] اعتماد التواقيع المقترحة: `اقرأ_ملف(Text) -> Result<Text>` و`اكتب_ملف(Text, Text) -> Result<Void>` و`عدد(Text) -> Result<f64>`؛ هذا تغيير سلوكي مقارنة بالمفسّر القديم، فيبقى المسار القديم موثقًا أو توفر أداة ترحيل صريحة. لا تغيير صامت قبل 1.0.
- [ ] حصر رموز الخطأ الأولية: `NotFound`، `PermissionDenied`، `InvalidUtf8`، `TooLarge`، `InvalidNumber`، `Io`؛ رسائل عربية ورمز ثابت، دون جعل نص رسالة نظام التشغيل واجهة برمجية. OOM وخطأ ABI/حدود غير آمنة أخطاء قاتلة موثقة، لا نجاحًا بقيمة فارغة.
- [ ] الحفاظ على سقف قراءة نص 2,000,000 بايت وتحديد ذلك صراحة في API؛ قراءة محدودة حتى مع ملف يكبر أثناء القراءة، تحقق UTF-8، ودعم NUL داخل المحتوى مع رفضه داخل المسار. الكتابة تستبدل المحتوى ولا تعد بالذرية؛ توثيق الروابط الرمزية والصلاحيات ومجلد العمل.
- [ ] إغلاق الملفات وتحرير buffers في كل مسار، معالجة الكتابة الجزئية وفشل flush/close، وتحديد سياسة المسارات العربية على كل نظام مدعوم؛ لا ادعاء sandbox.
- [ ] اختبارات أصلية: قراءة/كتابة عربية وفارغة، ملف مفقود، حد الحجم وما فوقه، UTF-8 تالف، مسار NUL، فشل كتابة محقون، وتمرير نتيجة بين الدوال. لا تعتمد اختبارات الصلاحيات على chmod فقط تحت root؛ استخدم harness لفشل I/O محدد.

**بوابة:** نجاح الفشل المتوقع قابل للاسترداد ثم استمرار البرنامج؛ تحققات فاشلة/فساد ذاكرة تعطي فشل عملية. اختبار تسرب متكرر يغطي نجاح الملفات وفشلها. يتوقف التنفيذ على عقد الذاكرة المشترك بدل تخصيص مسرّب لكل استدعاء.

## 3. وصف الحزمة وملف القفل وحل الاعتمادات

**الملفات المقترحة:** `src/packages/{mod,manifest,lock,resolve,cache}.rs`، `docs/PACKAGES.md`، `tests/packages.rs`، `tests/package_cli.rs`؛ إضافة `lisan.toml` و`lisan.lock` لأمثلة الاختبار فقط. اعتماد محلل TOML/SemVer مدقق بإصدار مقفل في Cargo.lock عند التنفيذ، لا parser نصي مرتجل.

**الحد الأدنى المقترح:** manifest فيه `package { name, version, entry }` و`dependencies`؛ الاعتماد المحلي يحدد `path` و`version`، واعتماد Git يحدد `git` و`rev` الكامل و`version`. `version` مجال SemVer، ونسخة manifest للاعتماد يجب أن تطابقه. لا registry ولا بحث تلقائي عن أحدث tag في المرحلة الأولى؛ مجال الإصدار يتحقق من مصدر صريح مثبت، ولا ينتج تنزيلًا متغيرًا.

- [ ] تحديد أسماء حزم ASCII ثابتة وقواعد اسم وحدة عربية منفصلة؛ منع تعارض هويات الحزم والمسارات والاستيرادات. `entry` والاستيرادات المحلولة داخل جذر الحزمة؛ الروابط أو `..` لا تتجاوز حدها صامتًا.
- [ ] تعريف `resolve(manifest, mode) -> LockedGraph`؛ mode هو `Update` أو `Locked` أو `Offline`. ترتيب traversal ومخرجات القفل ثابتان، اكتشاف الدورات، ورفض نسختين متعارضتين للاسم نفسه في المرحلة الأولى بدل خلط الرموز.
- [ ] تخزين صيغة القفل بإصدار، بصمة manifest، الهوية والمصدر والنسخة ومراجعة Git الكاملة وبصمة شجرة المحتوى وروابط الاعتماد. رفض المراجعات المختصرة والفروع المتحركة؛ لا مساواة SHA commit بـ checksum محتوى جرى نسخه أو تعديله.
- [ ] جلب Git بـ `Command` دون shell ومن دون submodules/hooks أو سكربتات حزم؛ حد مهلة وحجم، عدم تسجيل credentials، والتحقق من revision والمحتوى قبل نقل cache مؤقت ذريًا إلى هوية مثبتة. لا تنزيل خلال compilation المعتاد.
- [ ] المحلي يعمل بمساره القانوني؛ يحفظ القفل بصمة شجرته ويتحقق منها في locked، والتغيير يتطلب Update. استبعاد `.git` ونواتج البناء وفق قواعد ثابتة، ورفض الروابط الهاربة. لا تخزين مسار جهاز مطلق في قفل قابل للنقل؛ مسار نسبي داخل مشروع معروف.
- [ ] CLI أدنى: `lisan package resolve` يحدّث القفل/cache صراحة، و`lisan package resolve --locked` يتحقق دون تعديل، و`--offline` يمنع كل استدعاء شبكي ويشترط محتوى cache مطابقًا. البناء في مشروع ذي manifest يستعمل القفل ولا يعيد الحل تلقائيًا؛ يوضح خطأ الاعتماد المفقود أمر الإصلاح.
- [ ] وصل `LockedGraph` إلى loader عبر خريطة هويات إلى جذور مقفلة؛ اعتماد alias ووحدة استيراد للحزم يحدد في مواصفة الوحدات قبل تعديل grammar. يبقى استيراد الملفات القديم متوافقًا؛ لا تعديل `cwd` لحل الاعتمادات.
- [ ] اختبارات بمستودعات Git محلية مؤقتة: سلسلة اعتمادات، تغيير branch بعد القفل، rev مفقود، عدم تطابق SemVer، دورة، manifest متغير، cache تالف، خروج من الجذر وغياب cache في offline. اختبار أن offline لا يستدعي ناقل الشبكة أصلًا، وأن تكرار الحل يعطي نفس القفل ونفس البرنامج الأصلي.

**بوابة:** بناء مشروع متعدد الحزم من cache نظيف مُعبأ ثم مع تعطيل الشبكة، وتشغيل ناتجه الأصلي؛ لا hooks أو بناء تلقائي أثناء فتح المحرر. النشر العام والتوقيع وحل عدة إصدارات للاسم نفسه مراحل مستقلة.

## 4. VS Code وLSP فوق الواجهة ذات المواقع

**الملفات المقترحة:** `src/analysis.rs`، `src/bin/lisan-lsp.rs`، `tests/analysis.rs`، `tests/lsp.rs`؛ تعديل `editors/vscode/{package.json,README.md}` وإضافة عميل extension وملف قفل تبعياته. بروتوكول JSON-RPC عبر stdio؛ stdout رسائل البروتوكول فقط وstderr للسجلات.

- [ ] إضافة `analyze(entry, overlays, locked_graph) -> Analysis` كواجهة خدمة حول loader/parser/checker المشتركين؛ `Analysis { sources, diagnostics, symbols, references }`. لا تغير توقيع `checker::check` المنشور دون تنسيق؛ استخراج symbol/reference index من نفس مرحلة الربط، لا البحث بالاسم النصي بعد التحقق.
- [ ] overlays تخزن نصوص المستندات غير المحفوظة حسب URI وإصدار، وتُطبّق على imports أيضًا؛ `SourceId` وbyte `Span` من خطة النواة هما المصدر الوحيد للمواقع. لا Clang ولا تشغيل برامج ولا تنزيل حزم خلال التحليل.
- [ ] تنفيذ initialize/shutdown/exit وdidOpen/didChange الكامل/didClose ثم publishDiagnostics، definition، completion فقط. إعلان capabilities المنفذة، إعادة التشخيص بعد استيراد متغير، ومسحه عند الإغلاق/الإصلاح. لا نتائج قديمة بعد وصول إصدار مستند أحدث.
- [ ] التفاوض أو الالتزام بـ UTF-16 لمواقع LSP؛ محول صريح من byte span إلى line صفرية وUTF-16 column، مستقل عن عمود Unicode البشري في CLI. اختبار emoji قبل معرّف عربي، التشكيل وCRLF وحدود UTF-8.
- [ ] definition يرجع موقع التصريح الحقيقي في الملف الأصلي حتى بعد تحميل الوحدات؛ اختبار تظليل متغيرين عربيين، مرجع داخل دالة، ودالة مستوردة. completion يجمع الأسماء المرئية حسب النطاق وكلمات اللغة وAPI من السجل، ويرشح capabilities والتواقيع؛ لا يعرض متغيرًا خرج من النطاق.
- [ ] التعامل مع الشيفرة غير المكتملة عبر parser recovery أو تحليل آخر مقطع صالح، مع تشخيص محدد وحد موارد/إلغاء؛ لا تعطل خدمة المحرر بسبب فاصلة ناقصة. ملفات خارج المشروع/اعتمادات غير متاحة تنتج تشخيصًا دون جلب شبكة.
- [ ] عميل VS Code يشغل `lisan-lsp` بمسار قابل للضبط ووسائط منفصلة، لا shell؛ الاحتفاظ بالتمييز والمقاطع الحالية، وتوثيق تثبيت الخادم وإصدار البروتوكول وحدود الميزات. لا debugger أو rename أو format ادعاءً ضمنيًا.
- [ ] اختبارات JSON-RPC فعلية تفتح ملفًا عربيًا، تدخل خطأ نوعيًا وتصلحه، تفحص انتقال definition بين الوحدات وcompletion، تغلق الملف وتوقف الخادم؛ فحص extension package وتجربة Extension Host موثقة، دون نشر Marketplace تلقائي.

**بوابة:** التشخيص نفسه للملف المحفوظ يظهر في CLI وLSP برمزه وموضعه، مع تحويل إحداثيات صحيح؛ لا اختبار يصنع diagnostic داخل LSP بدل استهلاك الواجهة المشتركة.

## ترتيب التسليم والتحقق

1. السجل العددي والجرد يمكن إنجازهما أولًا؛ ملفات المضيف تنتظر Results وذاكرة القيم.
2. manifest/القفل/cache مستقل عن LLVM، لكن قبول البناء ينتظر loader مشتركًا ومطابقة الوحدات.
3. خدمة analysis وفهرس الرموز تنتظر located frontend؛ عميل VS Code يلي نجاح اختبار LSP عبر stdio.
4. يُشغّل `cargo test` مع مجموعات الاختبار الجديدة ثم اختبارات CLI الأصلية؛ اختبارات LLVM/runtime تبني وتشغّل ملفات فعلية، واختبار امتداد VS Code يستعمل أمر الحزمة المقفل المختار عند التنفيذ. تسجل الأدوات الغائبة كتخطي محلي وتفشل بوابة الإصدار المطلوبة.

كل مرحلة تنتهي بتقرير commit/الهدف/الأوامر والنتائج والقيود، وتحديث مربعات نطاق 1.0 المقابلة فقط. هذه الخطة لا تضيف دعم ملفات إلى freestanding أو متصفح، ولا تجعل نجاح المفسّر دليلًا للمكتبة الأصلية.
