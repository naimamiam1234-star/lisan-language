# خطة جودة لسان وقبول الإصدارات

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** إثبات صحة المسار الأصلي وموثوقية الإصدار بمخرجات تشغيل قابلة لإعادة التحقق.

**Architecture:** فصل native وlegacy والأهداف في وظائف قبول إلزامية، مع ربط متطلبات الإصدار بتقارير التنفيذ ومصفوفة التوافق.

**Tech Stack:** Rust/Cargo، Clang/LLVM، أدوات فحص الملفات الأصلية، GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-20-native-hardware-web-design.md` و`docs/LANGUAGE-1.0-SCOPE.md`.

## Global Constraints

- لا نجاح بلا اختبار منفذ، ولا مفسّر ضمن قبول native.
- توافق كل لوحة ومكتبة وهدف مستقل بإصدارات وأدلة.
- لا تُرفع الحالة دون دليل، ولا يُعامل غياب أداة مطلوبة كنجاح.

## Review Focus

- تجاوز الاختبار عند غياب Clang: P0 يتعمد إخفاء الأداة ويشترط الفشل.
- برنامج صحيح نحويًا ومرفوض أصليًا: P0 يختبر فشل `--check`.
- تغيير دلالة native تحت O2: P1 يقارن نواتج O0 وO2.
- فشل الربط أو تعارض وجهات البناء: P1 يحافظ على مصدر المستخدم والناتج السابق.
- نقل دليل لوحة إلى لوحة أخرى: P2 يرفض سجلات توافق ناقصة الهوية.

## قائمة تسليم قابلة للتتبع

- [ ] P0: اختبارات قبول لا تتجاوز الأدوات، وتصحيح عقد CLI وإثبات فشله ونجاحه.
- [ ] P1: حالات إعادة إنتاج واختبارات ارتداد وإصلاحات سلامة الحساب والذاكرة والبناء.
- [ ] P2: مخطط سجل توافق واختبارات رفض الأدلة غير الكافية.
- [ ] P3: حزم وإصدارات وأدلة تثبيت وإعادة بناء.
- [ ] P4: قبول أدوات المحرر والحزم بعد تنفيذ خطتها المتخصصة.

التاريخ: 2026-10-20. الحالة: خطة تنفيذ مستقبلية، لا دليل على نجاح إصدار أو اكتمال اللغة. النطاق: الاختبارات، دلالة واجهة الأوامر، سلامة المترجم، إثبات توافق المكتبات، وأدوات الإصدار. لا تعدّل هذه الوثيقة تنفيذ اللغة.

## معنى الاكتمال

لا تقاس لغة «مكتملة 100%» بعدد إصدار أو بنسبة تغطية الأسطر. قبل كل إصدار تُجمّد قائمة المتطلبات المدعومة، ولكل متطلب سلوك موثق واختبار قبول ودليل مطابق للهدف. الاكتمال يعني اجتياز جميع متطلبات تلك القائمة، مع إظهار الخصائص المؤجلة وحدود الدعم. لا يعني نجاح الاختبارات الحالية دعم كل مكتبة C/C++ أو كل لوحة أو الويب.

لم تُشغّل الاختبارات في هذه المراجعة: لم يعثر `command -v cargo` ولا `command -v clang` على الأداتين في بيئة العمل. كل نتائج التنفيذ المطلوبة أدناه «غير متحققة» حتى يُرفق سجل فعلي؛ وجود اختبار أو تعريف CI ليس نتيجة نجاح.

## مصفوفة قبول الإصدار

الحالة الحالية لكل صف: لم يُتحقق منه في هذه الجلسة. يحدد مرشح الإصدار الأنظمة ونسخ الأدوات المدعومة؛ تُحجب أي خانة لا تملك دليلًا بدل نقل نجاح منصة إليها.

| بوابة | الاختبار المطلوب | الدليل المحفوظ | معيار القبول |
| --- | --- | --- | --- |
| عقد اللغة | كل ميزة في مواصفة القواعد والأنواع: حالات صحيحة وخاطئة ومواقع أخطاء | قائمة متطلبات تربط كل معرّف باختبار | لا مطلب بلا اختبار؛ اختلاف متعمد عن المفسّر موثق |
| CLI | كل أمر، الوسائط الناقصة/الزائدة، مسار عربي/بمسافات، stdin/stdout/stderr ورمز الخروج | اختبارات subprocess وسجلات أو لقطات نصية | الاستخدام الخاطئ يخرج 2، فشل البرنامج/البناء يخرج 1، النجاح يخرج 0 وفق العقد المعتمد |
| الفصل بين الخلفيات | `file.lsn` و`--native` ينتجان آلة؛ `--emit-llvm` ينتج IR؛ `--interpret` و`--build` قديمان | تنفيذ فعلي وفحص object/symbols ومراجعة سلسلة البناء | لا رجوع صامت إلى المفسّر؛ كل تقرير يذكر backend |
| صحة LLVM | ملفات صحيحة تمثل جميع الفروع والحلقات والإرجاع والمنطق القصير | تحقق IR بواسطة أداة LLVM متوافقة ثم تجميع وتشغيل | لا يكفي `contains`؛ لا IR غير صالح؛ لا أخطاء أدوات مخفية |
| السلوك الأصلي | مقارنة stdout/stderr/exit بين المرجع والتنفيذ الأصلي للجزء المشترك | corpus ثابت مع نواتج متوقعة؛ تشغيل O0 وO2 | تطابق دلالي موثق؛ فروق متعمدة باختبارات مستقلة |
| السلامة | قسمة/باقي على صفر، NaN/Infinity، مدى، فهرسة، نصوص، تخصيص، إعادة بناء متزامنة | اختبارات سلبية ووقت أقصى وتشغيل أدوات تحليل ذاكرة حيث تدعم | لا crash أو UB أو تعليق غير محدود في حالات العقد؛ الأخطاء متوقعة |
| الاستيراد والملفات | ملفات مفقودة ودورات وUnicode وعمق/حجم غير معقول وصلاحيات | اختبارات `tests/modules.rs` وfixtures جديدة | خطأ واضح بلا انهيار، وحدود موارد معلنة |
| أهداف المضيف | تنفيذ الناتج على كل OS/معمارية معلنة؛ تثبيت Clang والموصل المطلوبين | سجل toolchain، بنية ELF/PE/Mach-O، stdout/exit | نجاح فعلي لكل خانة معلنة؛ غياب أداة يفشل الوظيفة |
| توافق C/C++ | استدعاء C حقيقي بتواقيع ثابتة؛ C++ عبر غلاف C معلن | source/object والرموز والتواقيع وإصدارات المكتبات | ABI وأحجام ومحاذاة صحيحة؛ التواقيع غير المدعومة مرفوضة |
| اللوحات | بناء image مطابق للوحة ثم Blink/UART وتطبيق المكتبة | linker map وحجم الذاكرة وسجل اللوحة/المحاكي | البناء وحده يحمل build-only؛ لا حالة hardware-tested بلا لوحة |
| المتصفح | wasm حقيقي وصفحة تستدعيه وDOM/أحداث/إدخال خاطئ | trace/نتيجة اختبار متصفح ونسخته | لا استخدام نجاح WASI لإثبات المتصفح |
| التوزيع | بناء من tag نظيف، فك الحزمة، تشغيلها دون Rust/Cargo، تجميع مثال بأدوات موثقة | manifests وchecksums وتقرير smoke | نسخة موحدة وملفات مطابقة؛ متطلبات Clang وقت البناء معلنة |

فحص الرموز وغياب السلسلة `Interpreter` قرينتان مساعدتان فقط؛ لا تكفيان لإثبات غياب مفسّر مضمن. يضاف فحص مسار البناء والاعتماديات وتشغيل في بيئة خالية من مصدر لسان ومن Rust/Cargo. تبقى libc المشتركة اعتماد تشغيل معلنًا عند استخدامها.

## أولوية P0: إزالة النجاح الكاذب وتثبيت عقد الأوامر

1. تعديل اختبارات Clang في `tests/native.rs` و`tests/native_extended.rs` لتفشل في الوظائف الإلزامية إن لم توجد الأداة أو أعاد `clang --version` حالة فشل. إضافة preflight موحد يسجل Rust وCargo وClang وLLVM والموصل والهدف، ثم يفشل قبل الاختبارات عند غياب متطلب.
2. تطبيق القاعدة نفسها على اختبار Cargo المتداخل في `tests/standalone.rs`. يجوز إبقاء مجموعة اختيارية للمطور بوسم صريح؛ تقريرها «لم تُشغل» وليس نجاحًا، ولا تُستخدم كدليل قبول. تشغيل مجموعات القبول بأسمائها وفرض حد أدنى معروف لعدد الحالات حتى لا يمر اختيار يشغّل صفر اختبار.
3. فصل وظائف native وlegacy في CI، وإضافة تنفيذ native الفعلي على Windows/macOS قبل إعلان دعمهما. إذا لم يُجهّزا بعد، تُعلن native Linux فقط. الاختبارات القديمة تظل مطلوبة لمنع كسر التوافق.
4. أول تسليم تنفيذي يضيف في `src/lib.rs` واجهة فحص native تستدعي frontend وتحليل الأنواع/القدرات دون ربط أو تنفيذ، ويربطها بـ `--check` في `src/main.rs`. إلى حين فصل تحليل الأنواع، يمكن استخدام نجاح توليد IR كفحص قابلية الخلفية بحدوده المعلنة؛ لا يُسمى تحليلًا شاملًا. يرفض الفحص أسماء غير معرفة واختلاط الأنواع والميزات غير المدعومة في native، مع إبقاء فحص legacy بخيار صريح موثق. ويجعل `--test` يبني برنامج native في مساحة مؤقتة خاصة ثم يشغله وينقل stdout/stderr وحالة الفشل، ويضيف خيار legacy صريحًا. يحدد harness وقتًا أقصى للاختبارات. لا يُستخدم نجاح المفسّر بديلًا عن native في المسار الجديد.
5. كتابة `tests/cli.rs` لاختبار `--help` و`--version` و`--check` و`--test` و`-e` و`--native` و`--emit-llvm` و`--build` والمسار الافتراضي. تتضمن حالات تثبت قبول parser لبرنامج يرفضه native ثم فشل `--check` الجديد، وفشل assertion فعلي عبر `--test` الأصلي، وغياب Clang، والفصل بين legacy وnative. تُحدّث رسائل المساعدة والوثائق مع تغير العقد، ولا يُعلن فحص أنواع قبل تنفيذه.
6. توحيد scripts المحلية مع وظائف CI: backend صريح، إخفاق فوري، stdout/exit متوقعان، ولا تنفيذ ملف بُني في محاولة سابقة. لا تجعل مجرد ظهور نص جزئي بـ grep معيار نجاح برنامج كامل.

قبول P0: تجربة مقصودة بإخفاء Clang تجعل وظيفة native حمراء، وتجربة بإفساد ناتج مثال تجعل مقارنة stdout حمراء، مع استمرار استقلال وظائف legacy. تحفظ سجلات التجربتين دون وصف التنفيذ غير المتاح بأنه ناجح.

## أولوية P1: صحة المترجم وسلامة البناء

الملفات الأساسية: `src/native.rs` و`src/runtime.rs` و`src/lexer.rs` و`src/modules.rs` و`src/bundle.rs`، مع اختبارات regressions جديدة قبل تصحيح كل عيب.

- **الأعداد:** يصدر native حاليًا `fdiv` و`frem` وpow دون حراس مكافئين لـ `finite_number` ومنع الصفر في المفسّر. قرر عقد الأعداد، ثم اختبر ±0، overflow، underflow، NaN الناتج، الأسس غير الصالحة، وتحويل النص والعدد والطباعة. لا تُخلط مساواة float بتسامح الاختبار؛ يُحدد التسامح حيث يلزم فقط.
- **مدى:** المفسّر يشترط أعدادًا صحيحة دقيقة وحدًا لطول القائمة، بينما native يولّد حلقة float تفحص الخطوة غير الصفرية. اختبر الكسور والقيم غير المنتهية وعدم تقدم الجمع بسبب دقة float، واتجاه الخطوة وحدود النهاية وbreak/continue. يختبر اختلاف الحدود بوصفه قرار لغة صريحًا أو يُصحح؛ لا يعدّ تلقائيًا خطأ أداء فقط.
- **عمر القوائم:** `build_numeric_list` يستخدم alloca في entry لتجنب نمو stack داخل loop، لكنه يعيد استخدام التخزين لنفس literal عند كل iteration. اختبر بقاء alias لقائمة من iteration سابقة، والإسناد عبر النطاقات، ونسخ/مرجعية القيم حسب العقد، وحجم stack؛ وجود حد 100000 لكل literal لا يحد مجموع stack.
- **النص والذاكرة:** `convert_to_text` والجمع يستخدمان malloc دون فحص null أو تحرير ظاهر. حدد ملكية/تحرير النصوص وعمر القيم، ثم اختبر OOM ونمو heap مع loop وتكرار التحويل؛ تحقق من overflow حساب طول الدمج. اختبر NUL المضمن وUnicode لأن puts/strlen/strcmp تعتمد النص المنتهي بصفر وقد تختلف عن Rust String.
- **التحكم والدوال:** تحقق LLVM وتنفيذ حالات return في الفرعين، حلقات متداخلة وshort-circuit مع فشل RHS، استدعاء متكرر/ذاتي، shadowing، إعادة تعريف، ومراجع متغيرات عامة من الدوال. لا توسّع قبول الأنواع دون IR معلوم الأنواع.
- **سلامة الملفات:** `build_native` يكتب IR باسم متوقع من PID واسم الناتج في مجلد الناتج، ويسمح بتمرير ناتج موجود إلى Clang. استبدله بمجلد خاص فريد ينشأ حصريًا مع cleanup، واختبر symlink والتوازي إلى نفس الوجهة وإخفاق الموصل. امنع تطابق source/output واستبدال ملف موجود افتراضيًا، أو اجعل الاستبدال خيارًا صريحًا. يُنشر الناتج بعد نجاح الربط فقط، مع حفظ الناتج السابق عند الإخفاق.
- **حدود الموارد:** fuzz لمدخلات UTF-8 والمحلل والاستيرادات وتوليد IR؛ كل مدخل لا يسبب panic/stack overflow/hang. ضع حدودًا موثقة للعمق والحجم ووقت subprocess في harness، واختبر الحدود نفسها. لا تنفذ fuzz programs دون عزل ووقت أقصى.

قبول P1: حالات إعادة إنتاج لكل فجوة، توافق الجزء المشترك، تحقق LLVM وتشغيل O0/O2، وتحليل ذاكرة على عينات native في الأهداف المتاحة. sanitizer مجرد جزء من الدليل، ولا يثبت سلامة دلالة اللغة وحده.

## أولوية P2: سجل توافق مكتبات قابل للتدقيق

إنشاء manifest للتوافق قابل للقراءة آليًا، وصف واحد لكل توليفة: معرّف الاختبار، commit لسان، target triple، ABI وعرض المؤشر، OS أو طراز اللوحة، core وإصداره، اسم المكتبة وإصدارها/commit، إعدادات build، نسخ الأدوات، fixture/adapter، حالة الاختبار، تاريخ التنفيذ، ورابط السجل. تضيف اختبارات العتاد رقم مراجعة اللوحة والذاكرة الفعلية وأسلوب القياس؛ لا تحفظ أسرار الشبكة أو Firebase في السجلات.

الحالات المسموحة: غير منفذ، بناء فقط، محاكاة، تشغيل مضيف، تشغيل متصفح، تشغيل على العتاد، فشل. «بناء فقط» لا يتضمن نجاح وظائف المكتبة. تغيير core أو إصدار المكتبة أو target يعيد الحالة إلى غير متحقق حتى إعادة الاختبار. لا تعني حالة المكتبة نجاح جميع واجهاتها؛ يسجل نطاق API والسيناريوهات صراحة.

الترتيب: دوال C نقية → أغلفة C لمكتبة C++ محددة → GPIO/UART للـ STM32F103C6T6A → I2C/SPI ومكتبة حساس/شاشة واحدة → أهداف ESP كل منها منفصل → الشبكة والمكتبات المعتمدة على الحسابات → واجهات المتصفح. تسبق كل مرحلة اختبارات رفض ABI غير المدعوم وفحص object والربط. تُراجع تراخيص المكتبات ومتطلبات التوزيع لكل حزمة فعلية، دون ادعاء توافق شامل مع Arduino.

## أولوية P3: إصدار موثوق وقابل لإعادة البناء

1. مصدر نسخة CLI هو `CARGO_PKG_VERSION`؛ تعرض `--version --verbose` المقترحة commit وtarget وإصدار toolchain بواجهة موثقة. توثق نسخة صياغة اللغة وABI وmanifest الحزم مستقلّة عند الحاجة؛ نسخة VS Code مستقلة مع مجال توافق معلن.
2. تتبع Cargo.lock لبرنامج CLI وثبت rust-toolchain وMSRV المعلن، ونسخ Clang/LLVM/الموصل لكل target مدعوم. شغّل CI بـ `--locked` بعد إضافة lock؛ لا تستخدمه في الخطة كأنه يعمل الآن. ثبت actions بمرجع immutable، وصور البناء بإصدار/digest متاح، وسجل الاعتماديات النظامية.
3. أضف gates مناسبة لـ fmt وclippy واختبارات الوحدات والتكامل والـ CLI وnative execution. افصل job العتاد المشروط عن البرمجيات؛ تأجيله يحجب وسم hardware-tested ولا يُخفى داخل success واحد. خزّن stdout/stderr وحالة الخروج وعدد الحالات ومدة التشغيل مع commit الهدف.
4. ابنِ حزم release من tag نظيف منفصل لكل target triple، بأسماء تشمل النسخة والهدف؛ ضم LICENSE وتعليمات البناء والتشغيل وعقد backend. أرفق manifest وSHA-256 وSBOM ومتطلبات النظام؛ تحقق من توقيع/provenance عند إضافته بدل الاكتفاء بوجود الملف.
5. جرّب الحزمة بعد التنزيل والفك في بيئة جديدة بلا Cargo: تشغيل مترجم لسان، ثم تجميع مثال بوجود Clang المعلن، ثم تشغيل ناتجه دون أدوات البناء. حزمة lisan ليست حزمة Clang ما لم تُضمّن الأداة وتوثق ذلك صراحة.
6. أنشئ بنائين نظيفين لنفس المدخلات المسجلة، واضبط المسارات والطوابع الزمنية اللازمة، وقارن الملفات وhashes. إذا اختلفا، انشر الفرق وسبب عدم الحتمية؛ لا تستخدم عبارة reproducible قبل نجاح المقارنة. ميز بين إعادة العملية بنجاح وبين تطابق البتات.
7. حدّث README وROADMAP وNATIVE-COMPILER وأسماء artifacts وخطوات CI بحيث لا تسمى native حزمة مفسّر، ولا تنفي LLVM الموجودة، ولا تحمل رقمًا مختلفًا عن الحزمة المنشورة. لا يثبت اسم artifact أو رقم الإصدار جودة أو دعمًا.

قبول P3: حزمة موثقة قابلة للتنزيل، checksum محقق، تثبيت نظيف ناجح لكل هدف معلن، تقرير فوارق/تطابق بنائين، وروابط أدلة تجيب عن كل صف في مصفوفة القبول.

## أولوية P4: أدوات التطوير واستقرار المنظومة

- **التشخيص وLSP:** يبدأ بمواضع المصدر ونطاقاته ونموذج تشخيص موحد من frontend، ثم خادم stdio يدعم initialization وdidOpen/didChange وpublishDiagnostics وshutdown. يختبر عدم تزامن النسخ وUnicode/UTF-16 offsets وعدم انهيار الخادم مع مستند غير مكتمل؛ definition وcompletion جزء من قبول 1.0 الأولي وفق خطة الأدوات، وتُؤجل hover وrename فقط. تختبر definition عبر الوحدات وcompletion حسب النطاق من نفس فهرس التحليل المشترك. إضافة syntax في VS Code الحالية ليست LSP. يجب أن يفهم التشخيص backend والهدف؛ فحص syntax وحده لا يؤكد صلاحية native.
- **مدير الحزم:** مواصفة manifest وأسماء الحزم والنسخ وحل التعارضات قبل registry؛ lock يحفظ المصدر والإصدار والhash والهدف/features. تبدأ fixtures محلية وoffline ثم registry موثق. تختبر إعادة الحل، الاعتماديات الدورية والمتعارضة، archive traversal وsymlink والchecksums، وإعادة البناء دون الشبكة. سكربتات build التي تنفذ كودًا تكون صريحة ومحدودة الصلاحيات، لا أثرًا ضمنيًا لتنزيل حزمة.
- **استقرار API/ABI:** مصفوفة تغييرات لغوية وكسر توافق وترحيل قبل إعلان إصدار مستقر؛ suites لبرامج قديمة وأغلفة مكتبات محفوظة. benchmarks ذات مدخلات ثابتة وقياس وقت/ذاكرة ومقارنة baseline مستقلة عن اختبارات الصحة. لا تستبدل جودة اللغة بعدد اختبارات أو نسبة coverage.

## ترتيب التسليم والدليل النهائي

P0 يسبق أي ادعاء نجاح جديد؛ إصلاحات P1 شرط رفع دعم native. P2 يعتمد على ABI/FFI والأهداف الفعلية في خطط التنفيذ الأخرى. P3 يُجهّز بالتوازي مع إصلاحات المترجم ويمنع نشر release غير موثق. P4 مراحل لاحقة مستقلة، لا تُحسب منجزة بوجود خارطة طريق.

تقرير كل مرشح إصدار يسرد: commit ونسخة، أهداف معلنة، عدد الاختبارات المنفذة والفاشلة والمؤجلة، قائمة الأدوات وإصداراتها، نتائج القبول لكل backend، حالات توافق المكتبات، links للأدلة، وقيود مفتوحة. أي اختبار لازم لم يُنفذ يجعل المتطلب «غير متحقق»، ولا تُستبدل النتيجة بوعد نجاح لاحق.
