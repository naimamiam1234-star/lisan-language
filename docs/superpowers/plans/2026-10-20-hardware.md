# Lisan Hardware Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Compile Lisan to target-specific objects and link them with Arduino cores and explicit C wrappers, proving STM32F103C6T6A first, then evaluating ESP32 DEVKITC V4 and ESP8266.

**Architecture:** Keep the direct AST → LLVM IR → machine-code path. A target contract governs ABI and runtime capabilities; Arduino owns startup, memory layout and setup/loop, while C wrappers bridge C++ libraries. Hardware support is a measured board/core/toolchain/library combination, never a claim covering all Arduino boards or libraries.

**Tech Stack:** Rust compiler, LLVM/Clang compatible with each target, board-supplied linker and runtime libraries, Arduino CLI, C/C++ wrappers; no embedded interpreter.

**Spec:** `docs/superpowers/specs/2026-10-20-native-hardware-web-design.md`

## Global Constraints

- “البداية بلوحة STM32F103C6T6A الخاصة بالمستخدم” — verify the actual device and C6 memory map; do not substitute C8 board defaults.
- “لا يصدر freestanding main أو استدعاءات malloc/printf ضمنيًا”.
- “يرفض البناء هدفًا غير مدعوم بدل الرجوع الصامت إلى جهاز المضيف”.
- “لا يُفترض أن Clang المثبت يدعم Xtensa”.
- “لا تُرفع الحالة دون دليل”. Build-only, simulation and hardware evidence are different states.
- This plan does not implement general C++ ABI, classes, templates, varargs, struct-by-value, callbacks, package management, volatile register access, or the separate browser/Wasm track.

## Review Focus

- An installed compiler can accept a target flag yet emit the wrong ABI: inspect ELF machine/attributes and execute a C/Lisan boundary test (Tasks 1–3).
- An Arduino C8 recipe can overflow or misaddress a C6 board: reject mismatched device/memory metadata and enforce linker limits (Task 3).
- Empty programs can retain implicit hosted dependencies: inspect undefined symbols and freestanding rejection paths (Task 2).
- Libraries retain pointers or allocate internally: wrappers define lifetimes and error paths, and tests cover invalid handles and failed initialization (Task 5).
- WiFi/SD/display pins and buses can conflict in combined sketches: record wiring and exercise shared SPI with independent chip-select lines (Task 5).

## Existing state and dependency gate

`src/native.rs` exposes `generate_llvm(&[Stmt])`, `emit_file(&Path)` and `build_native(&Path, &Path)`. It always emits `main`, declares libc, represents default numbers as double, assigns generated numeric function symbols, and hardcodes i64 in list lengths and libc size arguments. `src/main.rs` only has hosted native/IR switches. None proves target or Arduino support.

Before hardware acceptance, the native/FFI plan must deliver typed signed/unsigned integers, f32/f64, void, pointers, external declarations with explicit link names, exported functions with explicit symbols, signature checking, and a stable typed representation consumed by native generation. Keep legacy default number semantics for existing programs; never pass default double as a pin number or C integer implicitly. Export syntax must be specified/tested in the language-core plan; this document specifies ABI symbols, not unapproved Arabic grammar.

### Task 1: Define target contracts and fail-closed compiler selection

**Files:** Create `src/target.rs`, `src/target/abi.rs`, `tests/target.rs`, `tests/abi.rs`; modify `src/lib.rs`, `src/native.rs`, `src/main.rs`.

**Interfaces:** `Environment::{NativeHosted, Freestanding, Browser}`; `EmitKind::{Executable, Object, LlvmIr}`; `TargetSpec { id: String, triple: String, data_layout: String, pointer_bits: u8, size_type: types::Type, environment: Environment, cpu: String, features: Vec<String>, abi: String }`; `BuildOptions { target: TargetSpec, emit: EmitKind, compiler: PathBuf }`; `probe_target(&BuildOptions) -> Result<TargetProbe, String>`, where `TargetProbe` stores compiler identity, accepted target flags, object machine and ABI attributes. Target `size_type` uses the core `types::Type` enum and is constrained to `types::Type::Int { signed: false, bits: pointer_bits }`. Environment is carried by TargetSpec, not independently overridden. The canonical emitter is `generate_typed_llvm_with_options(program: &typed::TypedProgram, options: &BuildOptions) -> Result<String, Vec<Diagnostic>>`. Keep `generate_llvm_with_options(stmts: &[Stmt], options: &BuildOptions)` as an adapter that runs core resolution/type checking and invokes the typed emitter; never regenerate FFI signatures from untyped AST. `build_with_options(source: &Path, output: &Path, options: &BuildOptions) -> Result<PathBuf, Diagnostic>` uses that same checked pipeline. Preserve existing public helpers as hosted defaults. Define `LinkOptions { target: TargetSpec, linker: PathBuf, object_inputs: Vec<PathBuf>, library_paths: Vec<PathBuf>, libraries: Vec<String>, output: PathBuf }` and the source-free public helper `link_objects(options: &LinkOptions) -> Result<PathBuf, Diagnostic>`. Initially support validated hosted C ABI targets for this helper; board linking remains under the explicit core recipe in Task 3. Pass each object, library path and library argument separately without a shell; verify target machine/ABI, existence and nonempty object list before linking.

**Shared ABI interface:** `src/target/abi.rs` defines `trait CAbiLowering { fn lower_signature(&self, sig: &types::FunctionSig) -> Result<LoweredSignature, Diagnostic>; }`, using the core canonical typed signature. `LoweredValue { llvm_type: String, abi_attributes: Vec<String> }`; `LoweredSignature { calling_convention: String, return_value: LoweredValue, parameters: Vec<LoweredValue> }`. The result is the single authority for external declarations, exported definitions and call sites, including ABI attributes such as integer extension; an unsupported target/type combination returns a diagnostic. `TargetSpec::c_abi_lowering(&self) -> Result<Box<dyn CAbiLowering>, Diagnostic>` chooses only implemented profiles. Keep compiler-specific attribute policy in this module, not wrapper generation.

Assert emitted LLVM types and required ABI attributes against tiny C fixtures compiled by the selected target Clang; host test additionally links/runs C↔Lisan calls. ARM/browser tests compile and inspect matching objects with equipped tools; absent required tools fail the equipped job and provide no support evidence. Reject C ABI aggregates/varargs/callbacks outside the core FFI scope.
- [ ] Add `link_objects_runs_host_c_lisan_boundary`, `link_objects_rejects_empty_inputs`, `link_objects_rejects_machine_mismatch`, and `link_objects_preserves_argument_boundaries` to `tests/target.rs`; first test emits the typed Lisan object, separately compiles C, calls the public source-free linker, runs the resulting program and checks results.

- [ ] Add `unknown_target_is_rejected`, `missing_cross_compiler_is_rejected`, `target_probe_rejects_wrong_machine` and `hosted_helpers_keep_defaults` tests. The wrong-machine fixture returns an x86 object for an ARM request and must fail before linking.
- [ ] Run `cargo test --test target --test abi`; confirm new contract tests initially fail for missing implementation.
- [ ] Implement the contract and compiler invocation using argument vectors, never shell interpolation. Implement shared signature lowering and the source-free hosted linker alongside object emission. Specify `target triple` and `target datalayout` in IR; derive C size/pointer-related widths from the target contract, not host Rust `usize`. Probe compiler output, not just `--version`.
- [ ] Expose `--target ID`, `--emit-object`, `--freestanding`, `--compiler PATH`, `--output PATH` in CLI. Reject incompatible emit flags and cross-target executable attempts lacking an explicit board link recipe.
- [ ] Run `cargo test --test target --test abi` and existing native tests. Record unavailable tools as unavailable, never a passing cross-build.
- [ ] Commit the verified target-contract change.

### Task 2: Make freestanding objects a real compilation mode

**Files:** Modify `src/native.rs`; create `tests/freestanding.rs`, `tests/fixtures/hardware/empty.ll.expected-symbols` and typed source fixtures after grammar approval.

**Interfaces:** `RuntimeRequirements { heap: bool, io: bool, panic: bool, math: Vec<String> }`; `validate_runtime(requirements, Environment) -> Result<(), String>`. Typed exports must permit `void lisan_setup(void)` and `void lisan_loop(void)` with C ABI. These are the lifecycle contract consumed by Task 3.

- [ ] Add tests `empty_freestanding_has_no_main_or_hosted_symbols`, `print_requires_explicit_runtime`, `text_allocation_requires_explicit_runtime`, `checked_failure_requires_panic_hook`, `exports_keep_exact_symbols`, and `pointer_size_matches_target`. Inspect both generated IR and real object symbols; absence of declarations alone is not sufficient.
- [ ] Run `cargo test --test freestanding` and capture expected failures.
- [ ] Emit only needed runtime declarations/helpers. Reject unsupported print, allocation, checked-error and math paths with source diagnostics before writing output; math lowering can introduce compiler-runtime helpers, so collect and resolve those at link time. Initial hardware subset uses explicit integer operations and static data; doubles remain allowed only when the selected toolchain supplies the required ABI helpers and memory budget permits them.
- [ ] Compile with selected target/CPU/ABI and `-c`; emit no main, startup, libc link, or automatic `-lm`. Keep alloca/list lifetime and stack-budget restrictions explicit; reject escaping stack-backed list pointers across FFI.
- [ ] Run freestanding, native regression and real host C-wrapper tests, with `nm`/ELF inspection. Ensure generated objects contain lifecycle symbols and only declared wrapper/compiler-runtime imports.
- [ ] Commit the verified freestanding-object change.

### Task 3: Link STM32F103C6T6A Arduino firmware

**Files:** Create `hardware/targets/stm32f103c6.json`, `hardware/arduino/lisan_arduino.h`, `hardware/arduino/lisan_arduino.cpp`, `tools/build_arduino.py`, `tests/arduino_build.rs`, `examples/hardware/blink.lsn`, `examples/hardware/uart.lsn`.

**Interfaces:** Header exports `void lisan_setup(void)`, `void lisan_loop(void)`, `int32_t lisan_pin_mode(uint32_t pin, uint8_t mode)`, `int32_t lisan_digital_write(uint32_t pin, uint8_t level)`, `void lisan_delay_ms(uint32_t ms)`, `void lisan_uart_begin(uint32_t baud)`, `uint32_t lisan_uart_write(const uint8_t *bytes, uint32_t len)`. Wrapper constants map to core constants; pin/mode wrappers return 0 on success, 1 for invalid pin, 2 for invalid mode/level. Validate against the selected core pin table before invoking it. `setup()` and `loop()` are C++ core entry points invoking C ABI lifecycle symbols exactly once per core invocation.

- [ ] Add build tests for missing setup/loop, duplicate lifecycle definitions, wrong object machine/float ABI, missing core, and a C8 memory profile supplied under the C6 ID. All must fail explicitly without a host fallback.
- [ ] Run `cargo test --test arduino_build` and verify initial failures.
- [ ] Discover installed Arduino core/FQBN and compile properties; pin exact core and arm toolchain versions. Inspect actual C6 board support and linker script. Verify device documentation before setting flash/RAM limits; do not infer them from a C8 recipe or assume clone markings. ARM Cortex-M3/Thumb soft-float is the candidate contract, subject to actual recipe verification.
- [ ] Implement `tools/build_arduino.py --target stm32f103c6 --source FILE --out DIR`: preserve core startup, linker script, archive order, C++ initialization and compiler-runtime libraries. Disable cross-toolchain LTO initially to avoid incompatible LLVM/GCC bitcode. Compile wrapper with core C++ compiler and Lisan with LLVM; link ordinary objects with the board recipe.
- [ ] Emit ELF, board-selected flash image, linker map and manifest containing FQBN, device, core/tool versions, IR target, compiler flags, hashes, memory usage and unresolved symbols. Parse linker output and reject memory overflow.
- [ ] Build Blink/UART; inspect ELF machine/ARM attributes, symbols and section addresses. Unit-test lifecycle counts against a fake host Arduino core separately from cross-build acceptance.
- [ ] Commit the build integration; mark STM32 “built” only if real artifacts pass checks. No hardware claim yet.

### Task 5: Add peripheral and library wrappers one library at a time

**Files:** Create `hardware/arduino/libraries/{bus,st7735,bme280,tinygpsplus,sd,wifi}.{h,cpp}`, `tests/fixtures/hardware/wrappers/`, `examples/hardware/{display,weather,gps,storage,wifi}.lsn`; extend build tool and compatibility matrix.

**Interfaces:** Use fixed-width values, opaque `uint32_t` handles, explicit status codes (`0` success, nonzero documented errors), buffers plus byte lengths, and output pointers. Never expose `String`, classes or exceptions. Constructors allocate in C++ with explicit destroy functions or board-owned static instances; document ownership per API. Proposed contracts: `lisan_bme280_read(uint32_t handle, float *temperature, float *humidity, float *pressure)`, `lisan_gps_feed(uint32_t handle, uint8_t byte)`, `lisan_gps_position(uint32_t handle, double *lat, double *lon, uint32_t *age_ms)`, `lisan_st7735_fill(uint32_t handle, uint16_t rgb565)`, `lisan_sd_read(uint32_t handle, uint8_t *dst, uint32_t capacity, uint32_t *read_count)`, `lisan_wifi_status(void)`. All return `int32_t` except constructors returning status plus handle output. Exact library-specific init/create signatures are defined in the corresponding header before its Lisan fixture is written.

- [ ] Start with Wire/I2C and SPI wrappers and test invalid bus IDs/pins and short transfers against a fake core; cross-build and then test actual loopback/device communication on STM32 before dependent libraries.
- [ ] Pin Adafruit_GFX + ST7735 library versions; expose static initialization and fill/text primitives, explicit pin mapping and RGB565. Test invalid handles and failed init; build fixture then verify colors/orientation on the actual display.
- [ ] Pin BME280 dependency versions; expose init, explicit I2C address and status plus separate f32 outputs. Test absent-device failure and known fake readings, then capture actual readings without asserting invented sensor accuracy.
- [ ] Pin TinyGPSPlus; feed known recorded NMEA bytes and verify fix validity, age, position and malformed checksum rejection. Build target fixture; physical UART/GPS fix is a separate hardware test.
- [ ] Pin SD library/core pairing; expose open/read/write/close with bounded buffers and explicit byte counts. Test missing card, invalid handle, partial reads and capacity bounds. Use an expressly selected disposable test filename for board round-trip; record card filesystem and wiring.
- [ ] Add WiFi only on a board/core with a verified compatible networking implementation; STM32 base board has no assumed radio. Expose status, bounded credentials/configuration and connect/poll/disconnect with timeouts; redact credentials from logs. Build tests and physical access-point connection tests are separate.
- [ ] Build display + SD combined SPI fixture with distinct chip-select pins and bus configuration; hardware-test both together. Do not infer combined support from isolated demonstrations.
- [ ] For each wrapper separately, run its failing host boundary tests, implement the smallest API, pass host tests, produce cross artifacts and evidence, then commit. No library row inherits another row’s hardware status. Firebase is deferred until a compatible core/library/version and credential boundary are specified.

### Task 6: Probe ESP32 DEVKITC V4, then ESP8266

**Files:** Create `hardware/targets/esp32-devkitc-v4.json`, `hardware/targets/esp8266.json`, `hardware/evidence/{esp32-devkitc-v4,esp8266}/README.md`; extend `tests/target.rs`, build tool and compatibility matrix.

**Interfaces:** Reuse Tasks 1–5 contracts; each target manifest adds exact MCU/module, SDK/core and compiler identity, target attributes, memory/link recipe and supported wrapper list. Board marketing names are insufficient to select an instruction set.

- [ ] Identify the actual ESP32 DEVKITC V4 module/SoC. Determine selected core’s ABI and compiler flags. Identify exact ESP8266 module/flash profile separately.
- [ ] Probe the available LLVM distribution for each required Xtensa processor, features, relocations and object format. Upstream or installed Clang must not be presumed to support Xtensa; a vendor LLVM may be required, and available vendor compiler support must be verified for the chosen core/version rather than inferred from its name.
- [ ] Compile and link a tiny typed C↔Lisan integer/pointer/f32/f64 boundary fixture with the core toolchain; inspect symbols, relocation/ABI attributes and final linked artifacts. GCC compiling a C++ wrapper proves nothing about LLVM’s ability to generate the Lisan object. LLVM bitcode cannot simply be passed to GCC.
- [ ] If the backend cannot produce compatible objects, fail with “target backend unavailable” and keep target not-implemented. A future C transpiler would be a separately reviewed architecture change, not a silent fallback in this plan.
- [ ] If probes pass, add target contracts, build Blink/UART and repeat physical acceptance for ESP32 first, ESP8266 second. Confirm loop yields/watchdog behavior follows each core; keep lifecycle callbacks free of unbounded blocking work.
- [ ] Evaluate WiFi, SD, ST7735, BME280 and TinyGPSPlus independently with the exact versions and wiring for each board. Check memory budgets and combined SPI behavior anew; no compatibility inheritance from STM32 or between ESP families.
- [ ] Commit only verified target contracts/evidence and update status accordingly.

## Release gate and commands

Run `cargo test`, then selected real toolchain jobs with `python3 tools/build_arduino.py --target stm32f103c6 --source examples/hardware/blink.lsn --out build/hardware/stm32-blink`. The CLI is proposed by this plan and does not exist today. CI must distinguish compiler-unit jobs, required equipped cross-build jobs and optional physical jobs; missing required tools fail the equipped job, while ordinary developer runs report prerequisites without pretending to cross-compile. Inspect map/ELF with the selected toolchain’s `readelf`, `nm`, `objdump`, and `size` tools. Before marking any target built, archive exact flags, tool identities and artifact hashes. Before marking hardware-tested, attach physical evidence for that exact artifact.

This document is a future implementation plan. No firmware, cross-toolchain probe or physical test is claimed to have run while writing it. Typed FFI/exports, confirmed C6 core support/memory profile, compatible ARM LLVM ABI, physical board access, and Xtensa LLVM availability remain explicit dependency gates.
