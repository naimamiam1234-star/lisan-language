# Browser WebAssembly implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Status: proposed implementation steps, not a claim of implemented browser support. Based on `src/native.rs`, `src/main.rs`, and the 2026-10-20 native/hardware/web design. This document owns only the browser workstream; the typed ABI and target-description workstream must land first.

**Goal:** Produce a compiled wasm32 browser program with Arabic text, DOM updates, and events.

**Architecture:** Shared typed LLVM lowering plus a selected browser runtime, explicit wasm imports/exports, and a small JavaScript host.

**Tech Stack:** Rust compiler, LLVM/Clang, wasm-ld, freestanding runtime C, ES modules, Playwright Chromium.

**Spec:** `docs/superpowers/specs/2026-10-20-native-hardware-web-design.md`.

**Global Constraints:** No interpreter or host fallback; no WASI conflation; common core owns types/target ABI; only explicit browser imports; report unexecuted verification honestly.

**Review Focus:** Pointer widths, cross-boundary ownership, Unicode, runtime symbol closure, listener lifecycle, and actual browser execution.

## Scope and present blockers

Compile Lisan through LLVM to a real `wasm32-unknown-unknown` module, loaded by JavaScript in a browser. No AST evaluator, embedded interpreter, source evaluation, or fallback to the host executable is permitted. WASI is a distinct future environment; neither `wasm32-wasi*`, `_start`, nor `wasi_snapshot_preview1` is accepted for this browser target.

Today `generate_llvm` unconditionally emits native `main` and libc declarations. `Type::NumberList` is `{ i64, ptr }`; list loops, GEP indices, `strlen`, allocation and `snprintf` sizes use i64. Strings are NUL-terminated pointers; number conversion leaks allocations; list literals point at function-local stack storage. Numeric functions are mangled internal symbols without a public export contract. Changing only the Clang triple cannot produce a safe browser ABI.

## Stage 1: target and runtime separation

Files: extend the shared planned `src/target.rs`; modify `src/native.rs`, `src/lib.rs`, `src/main.rs`; add `src/wasm.rs`, `tests/wasm_codegen.rs`.

- [ ] Land target/runtime separation and wasm build entry point.
- [ ] Add explicit CLI validation and toolchain probes.
- [ ] Execute scalar wasm and native regression acceptance checks.

- Represent shared `TargetSpec { id, triple, data_layout, pointer_bits, size_type, cpu, features, abi, environment }` with explicit `Environment::NativeHosted`, `Freestanding`, and `Browser`; use shared `BuildOptions` for tool paths, target and output policy. Browser is wasm32, pointers and `usize`/allocation lengths are i32, linear memory addresses are unsigned 32-bit offsets. Lisan `i64` remains i64 when explicitly requested; default numbers remain f64. Do not mechanically change semantic integer widths with pointer widths.
- Match the hardware/core contract: `size_type` is an unsigned pointer-width `types::Type::Int`; common `src/target/abi.rs` owns `CAbiLowering`. The canonical emitter is `generate_typed_llvm_with_options(&typed::TypedProgram, ...)`; legacy untyped generation is an adapter. Browser build must consume that typed entry point and its ABI policy.
- Generate target-specific LLVM triple and data layout, validated against the selected toolchain. Parameterize list layout, GEP/address arithmetic, `ptrtoint`/`inttoptr`, allocation and length signatures. Check conversion overflow before narrowing. Audit every hard-coded `i64` in `src/native.rs`.
- Add `pub fn build_browser(source: &Path, output: &Path, options: &BuildOptions) -> Result<PathBuf, String>` in `src/wasm.rs`; retain the existing native API as a native wrapper. Share lowering instead of copying the compiler or invoking the interpreter.
- Proposed CLI: `lisan --target browser-wasm32 --output dist/app.wasm examples/web/counter.lsn`. The target ID fixes LLVM triple `wasm32-unknown-unknown` and `Environment::Browser`; environment is not independently overridable. `--emit-llvm` must accept the same target ID. Reject conflicting `--freestanding` or native-only switches before creating output. Existing `--native`, default `.lsn`, and legacy `--build` retain their meanings.
- Use `Command` arguments, never shell interpolation. Probe Clang wasm backend and wasm-ld before compilation. Link with explicit `--target=wasm32-unknown-unknown -nostdlib -Wl,--no-entry`, explicit exports/import declarations and memory bounds; never `--allow-undefined` globally. Add a documented reproducible LLVM version in CI. `cargo build --target wasm32-unknown-unknown` alone builds the Rust compiler for wasm and is not this language backend.

Acceptance: wasm magic/version bytes; module validates; memory is wasm32; public scalar function returns 42 in a JavaScript WebAssembly instance. Module imports contain only the declared `lisan` namespace, no libc, WASI, `main`, or interpreter symbols. Native tests continue passing.

## Stage 2: libc-free browser runtime and ownership

Files: add `runtime/browser/runtime.c`, `runtime/browser/abi.h`, `docs/web-abi.md`; modify runtime selection in `src/native.rs`; add `tests/wasm_runtime.rs` and `tests/fixtures/web/`.

- [ ] Specify shared text/list ownership with compiler core before representation changes.
- [ ] Implement runtime helpers, allocation/free, and UTF-8 ABI checks.
- [ ] Execute allocation, memory growth, Unicode, and error acceptance checks.

- Compile the small C runtime as freestanding wasm object with `-ffreestanding -fno-builtin -nostdlib`; implement checked allocation/free, byte copying, UTF-8 byte length, concatenation, and byte comparison without host libc. Compiler-emitted helper calls use `lisan_rt_*`, not `malloc`, `printf`, `snprintf`, `strcpy`, `strcat`, `strlen`, `strcmp`, `puts`, or `exit`. Audit final undefined symbols to catch LLVM lowering into helper libc calls.
- Coordinate length-bearing internal text values `{ usize, ptr }` and lifetime rules in the shared compiler-core contract first; this is a dependency, not permission for an incompatible browser-only `Type::Text` fork. Use explicit byte lengths at the JS boundary. Embedded NUL is valid. Literals are immutable module-owned data; concatenation returns owned heap data. Lists that escape a function must own heap storage rather than return stack pointers. Until shared ownership lands, reject escaping heap aggregates and unsupported text operations explicitly.
- Export `lisan_alloc(len: i32) -> i32` and `lisan_free(ptr: i32, len: i32) -> void`. Zero means allocation failure for nonzero length. Use alignment and overflow checks, validated allocation metadata, a free list or equivalent reuse, explicit maximum memory, and a defined zero-length convention. Repeated events must not cause monotonic unbounded allocation. Exported raw pointers are an ABI facility, not arbitrary safe Lisan pointers.
- JS owns input allocations: allocate, refresh the typed view after allocation/memory growth, copy TextEncoder bytes, invoke a synchronous export, then free in `finally`. Wasm borrows those bytes only for the call; retaining text requires a runtime copy. Wasm owns static and temporary output; imports copy/decode synchronously before returning. No host code frees literals. For exported result strings use a caller-provided buffer plus required-length/status result, rather than an undocumented persistent pointer.
- Export memory; host reads `instance.exports.memory` after instantiation. Never retain typed-array views across calls which can grow memory. Normalize numeric wasm i32 pointers and byte counts with `>>> 0` before checking. Bounds checking uses `ptr <= byteLength` and `len <= byteLength - ptr` to avoid integer overflow. Use `DataView.setUint32(required, length, true)` for little-endian required-length writes and `getUint32(..., true)` for reads; do not assume host typed-array endianness or unvalidated alignment. Decode UTF-8 with fatal errors for ABI text; use TextEncoder for inputs. Test Arabic, diacritics, emoji, empty text, embedded NUL and invalid UTF-8.
- Replace guard `puts`/`exit` with `lisan.report_error(ptr,len)` followed by a trap, or an explicit status return at recoverable exported boundaries. Preserve source location where available. Specify numerical support per operation: floor/sqrt map to supported wasm operations; pow/round or formatting need a real freestanding implementation or a documented explicit host import. Reject unsupported operations at compile time until implemented, with no accidental `-lm` dependency.

Acceptance: actual wasm instantiation and text/list execution; no undeclared imports; allocation reuse and OOM failure; forced memory growth; errors surface in the page. Leaking a buffer per click fails acceptance.

## Stage 3: exports, DOM, and event bridge

Files: add `web/lisan-host.mjs`, `examples/web/counter.lsn`, `examples/web/index.html`, `examples/web/style.css`, `examples/web/app.mjs`; modify semantic checking/lowering and explicit export support in the shared typed ABI implementation. Add `docs/web.md`.

- [ ] Implement validated import/export signatures and callback dispatch.
- [ ] Implement the host bridge and compiled Arabic demo.
- [ ] Execute DOM, invalid-input, isolation, and disposal acceptance checks.

Use the common typed foreign declaration/export feature, not special parser hacks for this demo. Final Arabic syntax follows the shared grammar specification. Validate unique external export names and signatures, emit unmangled public names, and reserve only `lisan_fn_*` and `lisan_rt_*` for compiler/runtime internals. The explicit public wrappers `lisan_init`, `lisan_dispatch`, `lisan_dispose`, `lisan_alloc`, and `lisan_free` remain legal, unique exports. Export scalar values as wasm i32/i64/f32/f64; use 0/1 i32 booleans at the JS boundary. Reject aggregate by-value exports, untyped callbacks, and implicit narrowing. JavaScript i64 uses BigInt when enabled and must never silently pass through Number.

Initial explicit import contract (module name `lisan`):

| Import | Signature | Contract |
| --- | --- | --- |
| `log_utf8` | `(ptr:i32,len:i32)->void` | Copy/decode during call; map printing here |
| `set_text` | `(element:i32,ptr:i32,len:i32)->i32` | Set `textContent`; 0 success, nonzero error |
| `read_value` | `(element:i32,out:i32,capacity:i32,required:i32)->i32` | Status 0 success, 1 insufficient capacity, 2 bad handle, 3 invalid memory; write UTF-8 byte count to aligned `required` on statuses 0/1 |
| `listen_click` | `(element:i32,callback:i32)->i32` | Register an approved callback ID; return listener handle |
| `unlisten` | `(listener:i32)->void` | Idempotent cleanup |
| `report_error` | `(ptr:i32,len:i32)->void` | Copy error into page error region |

Host resolves allowed DOM elements once into opaque positive handles; unknown handles fail deterministically. Do not pass JavaScript object addresses or expose arbitrary HTML insertion. `read_value` validates the four-byte aligned required-length destination first, then the element and output range. Capacity and lengths are unsigned wasm32 bytes; reject encoded values above 0x7fffffff with status 4. On insufficient capacity write only required length, never partial text. On other failures write no memory. Zero capacity may query length with out=0. Caller retries after allocation and refreshes memory views.

Export `lisan_init()->i32`, `lisan_dispatch(callback:i32)->i32`, and `lisan_dispose()->void`; each callback ID maps to a compiled Lisan function with validated signature. JavaScript event listeners invoke dispatch only after successful init. No function-pointer casts between JS and wasm are needed. Keep listeners in a host map, unregister on dispose, reject unknown callbacks, and handle errors per event. Loading uses fetch plus instantiateStreaming with a MIME-compatible arrayBuffer fallback, no start function calling DOM imports before exports/memory exist.

Demo: Arabic RTL page, labeled numeric input, action button, result and live error region. Lisan computes the result and validates input; JS only loads the module, marshals values, and bridges DOM. Empty/invalid/nonfinite input displays an Arabic error; a later valid submission recovers. Time/network imports are separate future additions with an explicit asynchronous completion ABI; do not pretend synchronous wasm imports can directly await fetch.

Acceptance: click executes a compiled export and changes DOM; JS contains no reimplementation of the arithmetic/validation; two mounted instances have isolated handles/memory; dispose/remount produces one callback per click.

Proposed commands after implementation:

```sh
cargo test
cargo run -- --target browser-wasm32 --output examples/web/app.wasm examples/web/counter.lsn
wasm-tools validate examples/web/app.wasm
wasm-tools print examples/web/app.wasm
npm --prefix web ci
npm --prefix web exec playwright install chromium
npm --prefix web test
```

`web` package test starts a local HTTP server with wasm MIME support, launches Chromium, and fails on missing wasm, failed fetch/instantiation, page errors, unexpected console errors, or undeclared imports. Tool absence may skip a local integration test with a specific reason; the release CI job must fail if required tools are missing. No success claim from LLVM text matching alone.

Browser tests cover initial result; valid Arabic text round trip; invalid numeric input and recovery; repeated clicks; listener cleanup; unknown DOM/callback handles; forced memory growth; malformed UTF-8/bounds; OOM; CSP-compatible module loading; absence of WASI imports. Capture a screenshot and machine-readable test report as evidence, but assert DOM text and export results rather than relying on screenshots. Artifact inspection must show wasm executable code and expected import/export lists; deny source/AST/interpreter payloads and host executable fallback.

Release gate: all shared/native tests pass; wasm validates; browser integration tests execute real generated module; docs name exact tested tools and supported operations. Publish status as browser-tested only with those results. Full-language browser parity, general networking, threads, arbitrary C libraries, and WASI remain separate milestones until their own contracts and tests exist.
