# لسان: مواصفة التجميع الأصلي والعتاد والويب

الحالة: مقترح للمراجعة، وليس إعلان دعم منفذ. التاريخ: 2026-10-20.

## الهدف

تطوير لغة عربية مكتوبة بـ Rust، تُجمّع مسبقًا إلى تعليمات المعالج دون مفسّر مضمّن. دعم مكتبات Arduino عبر ربط ثنائي واضح، وتشغيل برامج الويب عبر WebAssembly. لا يعني هذا ضمان تشغيل كل مكتبة وكل لوحة؛ التوافق خاص بإصدار المكتبة واللوحة وأدوات البناء.

## نتائج مراجعة النسخة الحالية

- `src/native.rs` يحول AST إلى LLVM IR ثم يستدعي Clang لإنشاء برنامج أصلي. المسار الافتراضي في `src/main.rs` يستخدمه بالفعل.
- القيم الحالية: double وboolean ونص وقائمة أرقام. معاملات الدوال ونتائجها رقمية فقط.
- توليد الشيفرة يفترض واجهات مكتبة C مثل malloc وprintf وstrlen، وبعض الأطوال ثابتة كـ i64. لا يصح نقل هذه الافتراضات تلقائيًا إلى أهداف 32 أو 8 بت.
- `--build` القديم يضم المفسّر؛ يبقى للتوافق ويجب وصفه بوضوح، ولا يُستخدم في أي اختبار قبول للدعم الأصلي.
- لا يوجد حاليًا FFI أو اختيار هدف أو مسار Arduino أو متصفح في المترجم الأصلي.
- لم تُنفذ الاختبارات في جلسة المراجعة: أمر cargo غير متوفر في البيئة. لا توجد نتيجة نجاح جديدة.

## القرار المعماري المقترح

الاحتفاظ بخلفية LLVM الحالية وتوسيعها. البديلان هما توليد تعليمات كل معالج يدويًا، أو تحويل كامل اللغة إلى C/C++؛ الأول يضاعف عبء الخلفيات والثاني لا يحقق رغبة المستخدم في مسار LLVM المباشر. استخدام Clang وموصل النظام وقت البناء لا يضيف مفسّرًا إلى البرنامج الناتج.

تُقسم المنظومة إلى واجهة لغة، وتمثيل وسيط مع أنواع، وخلفية توليد، ووصف هدف، وواجهة بيئة تشغيل. يبدأ دعم مكتبات C عبر C ABI؛ مكتبات C++ تحتاج أغلفة `extern "C"` أو مولد ربط لاحقًا. لا يُدّعى دعم C++ ABI أو القوالب أو الأصناف مباشرة.

## المرحلة الأولى: عقد الأنواع والربط الأصلي

هذه أول وحدة تنفيذ مقترحة، وتسبق الويب واللوحات:

1. إضافة أنواع صريحة للأعداد الصحيحة الموقعة وغير الموقعة بعرض 8 و16 و32 و64 بت، وf32 وf64 والمنطقي وvoid والمؤشرات. تحتفظ البرامج القديمة بنوع العدد الافتراضي الحالي.
2. إضافة تعريف دالة خارجية باسم ربط منفصل، ومعاملات ونتيجة محددة الأنواع. تُحدد الصياغة العربية في مواصفة قواعد اللغة قبل تعديل lexer وparser؛ هذه الوثيقة لا تثبت صياغة غير مختبرة.
3. رفض التحويلات الضيقة أو تغير الإشارة الضمني في حدود FFI. منع التصريحات المتعارضة والرموز غير الصالحة. لا تدعم المرحلة الأولى varargs أو struct-by-value أو callbacks أو C++ مباشرة.
4. السماح بإخراج ملف object وربط ملفات object ومكتبات ثابتة عبر خيارات CLI مستقلة؛ تمرير الوسائط إلى Command دون shell.
5. فصل التشغيل المستضاف عن freestanding. لا يصدر freestanding main أو استدعاءات malloc/printf ضمنيًا، وتُرفض الخصائص المحتاجة إلى بيئة تشغيل غير متوفرة.
6. وصف الهدف يحدد triple وdata layout وعرض المؤشر وABI والأدوات المطلوبة؛ يرفض البناء هدفًا غير مدعوم بدل الرجوع الصامت إلى جهاز المضيف.

اختبار القبول: تجميع برنامج لسان وربطه مع دالة C فعلية، وتشغيل الناتج والتحقق من القيمة، وفحص رمز الربط وتعليمات المعالج؛ اختبار رفض التواقيع الخاطئة؛ التحقق من استمرار اختبارات النسخة القديمة. فحص LLVM نصيًا وحده لا يكفي.

## المرحلة الثانية: Arduino والعتاد

- البداية بلوحة STM32F103C6T6A الخاصة بالمستخدم، بعد تثبيت core ونسخة سلسلة أدوات موثقة. يلزم تعريف ذاكرة مطابق لطراز C6 وعدم استخدام افتراضات C8.
- تصدر لسان object مطابقًا لـ ARM ABI، ويربط مع startup وlinker script وArduino core وأغلفة C/C++ الخاصة باللوحة. لا يمكن استخدام ELF المضيف على المتحكم.
- يدير غلاف core دورة setup/loop، ويستدعي نقطتي دخول لسان صريحتين. تبدأ الواجهات بـ GPIO والتأخير وUART ثم I2C وSPI.
- Blink واختبار UART يتطلبان تحققًا على اللوحة. يسجل اختبار البناء دون لوحة بوصفه build-only، ولا يُسمى اختبار عتاد ناجحًا.
- ESP32 DEVKITC V4 وESP8266 يحتاجان خلفيات وأدوات متوافقة مع معالجاتهما؛ لا يُفترض أن Clang المثبت يدعم Xtensa. تُفحص الأدوات قبل إعلان الهدف.
- مكتبات مثل Adafruit_GFX وST7735 وBME280 وTinyGPSPlus وSD وWiFi تضاف واحدة واحدة بأغلفة وإصدارات واختبارات. Firebase يتطلب مكتبة متوافقة مع core المختار وإدارة الاعتمادات.
- الوصول المباشر إلى سجلات الأجهزة يحتاج عمليات volatile ومحاذاة وعروض صحيحة ومناطق unsafe معلنة؛ لا يحل استدعاء دالة تحمل اسم GPIO هذه المتطلبات.

## المرحلة الثالثة: الويب

- هدف wasm32 مستقل عن native، بلا اعتماد افتراضي على libc المضيف.
- واجهات JavaScript صغيرة ومعلنة للذاكرة والنصوص وDOM والأحداث والوقت والشبكة. HTML وCSS يصفان الصفحة، وWebAssembly ينفذ منطق لسان.
- فصل متصفح WebAssembly عن WASI؛ نجاح برنامج WASI لا يثبت عمل DOM أو المتصفح.
- قبول أولي: ملف wasm فعلي، وصفحة تستدعي دالة منه وتعرض الناتج، واختبار متصفح يتحقق من العرض ومعالجة خطأ الإدخال.

## المراحل اللاحقة

نظام وحدات وحزم بإصدارات وملف قفل، إدارة ذاكرة محددة، دوال النصوص والقوائم بأنواعها، قواميس، رسائل أخطاء بمواقع المصدر، LSP، ومكتبة قياسية مستقرة. كل مرحلة لها مواصفة واختبارات؛ لا تُجمع تحت وعد «كل شيء» غير قابل للتحقق.

## قواعد الإعلان عن التوافق

جدول الدعم يسجل: الهدف، طراز اللوحة، core، المترجم والموصل، المكتبة وإصدارها، نوع الاختبار وتاريخه. الحالات: غير منفذ، بُني، اختُبر بمحاكاة، اختُبر على العتاد. لا تُرفع الحالة دون دليل. يبقى الفشل عند غياب سلسلة الأدوات واضحًا ولا يُستبدل بمفسّر أو برنامج مضيف.
