# خارطة تطوير لسان 1.0

تاريخ الخطة: 2026-10-20. الحالة: خطط مقترحة للتنفيذ، وليست ميزات منجزة.

## معنى الاكتمال

«100%» تعني اجتياز متطلبات إصدار محدد منشور، لا التوافق مع كل برنامج ومكتبة وجهاز في العالم. لا تعد ميزة مكتملة بمجرد كتابة ملفاتها؛ يلزم اختبار قبول وتوثيق قيود ودليل بناء وتشغيل. ينفذ المنتج النهائي برامج أصلية دون مفسّر لسان مضمّن.

## ترتيب التنفيذ وبوابات القبول

| المرحلة | المتطلب السابق | التسليم القابل للتحقق | دليل القبول |
|---|---|---|---|
| 0: خط أساس موثوق | أدوات Rust وClang | اختبارات المسار الأصلي منفصلة عن القديم | سجل CI لا يخفي غياب أداة كتجربة ناجحة |
| 1: سلامة النواة | 0 | تشخيص دقيق وحسابات وذاكرة بعقد واضح | اختبارات حالات الفشل والحدود وبرامج أصلية فعلية |
| 2: الأنواع والواجهات | 1 | أعداد صحيحة ومؤشرات ودوال محددة الأنواع وC ABI | استدعاء متبادل مع C ومقارنة النتائج وفحص الرموز |
| 3: أهداف البناء | 2 | object وبيئة freestanding ووصف الهدف | فحص معمارية object ومنع الربط بمعمارية غير مطابقة |
| 4A: STM32/Arduino | 3 | برنامج setup/loop وGPIO/UART | بناء firmware ثم تشغيله على STM32F103C6T6A |
| 4B: WebAssembly | 3 | ملف wasm وصفحة تتفاعل معه | اختبار متصفح فعلي وذاكرة UTF-8 واستدعاءات DOM |
| 5: المكتبات | 4A | أغلفة لمكتبات محددة بإصدارات | اختبار منفصل لكل مكتبة ولوحة وتبعياتها |
| 6: أدوات اللغة | 2 | حزم ومحرر وLSP وتشخيص ومكتبة قياسية | اختبارات تثبيت وبناء من بيئة نظيفة وفق عقد 1.0 |
| 7: إصدار 1.0 | المتطلبات الإلزامية في عقد الإصدار | إصدار موثق مع مصفوفة دعم | جميع بوابات الإصدار ناجحة، دون عناصر إلزامية معلقة |

يمكن تنفيذ 4A و4B بالتوازي بعد تثبيت واجهات المرحلة 3. لا يعد ESP32/ESP8266 مجرد تغيير اسم الهدف؛ يلزم التحقق من خلفية المعالج وسلسلة أدواته. دعم ARM أولًا لا يثبت دعم Xtensa أو AVR.

خطة القيم المُدارة تتبع النواة وتسبق تمكين النصوص والمجموعات العابرة للدوال والحدود. لا تعني إمكانية بناء wasm عددي بسيط اكتمال ذاكرة تطبيق متصفح طويل التشغيل. يعتمد تنفيذ المكتبة القياسية المتقدمة على هذه القيم وعلى عقد الأخطاء في خطة الأدوات.

## قواعد عمل الوكلاء أثناء التنفيذ

1. لكل مهمة ملكية ملفات محددة وواجهة معلنة. يتولى مالك واحد تغييرات AST/parser/native المشتركة.
2. يكتب صاحب المهمة اختبار القبول قبل التعديل ويثبت فشله ثم نجاحه. توثق العوائق إذا تعذر تشغيل الأدوات.
3. يراجع وكيل آخر الفرق ومتطلبات المهمة؛ مراجعة الخطة لا تُسجل كمراجعة للشيفرة المنفذة.
4. يدمج المنسق المهام التابعة بعد تثبيت الواجهات ثم يشغل اختبارات التكامل.
5. الحالات المسموحة: مخطط، قيد التنفيذ، محجوب، اجتاز الاختبار، مدمج. لا تحول كلمة «موجود» إلى «يعمل».

## الوضع الحالي

المترجم 0.8 يولد LLVM وكود آلة لمسار محدود. لم تُضف أنواع FFI أو Arduino أو wasm أثناء مرحلة التخطيط. Rust/Cargo وClang غير متاحة في PATH بهذه البيئة، لذلك لا توجد نتائج اختبارات تنفيذية جديدة. لا تزال شيفرة المنتج عند خط الأساس الحالي.

## أول حزمة تنفيذ

إعداد خط أساس موثوق وإغلاق التفاوت بين فحوص CLI والمترجم الأصلي، ثم سلامة العمليات العددية وإدارة ملفات البناء. يليها عقد الأنواع وFFI. لا يبدأ بناء أغلفة المستشعرات أو DOM قبل استقرار هذه الواجهات.

تُراجع الخطط المتخصصة كحزمة واحدة؛ الصياغة النحوية والأسماء والواجهات المقترحة فيها لا تصبح واجهة لغة مستقرة حتى تُدمج مع اختبارات القبول.
